## Abstract

A merchant delegates offer creation to a point-of-sale (PoS) terminal. The PoS
constructs per-order offers from a merchant-provided template, adding an
encrypted payment token and a notification blinded path. When the customer pays,
the merchant notifies the PoS via onion message. The PoS never touches customer
funds and is not on the payment path.

## Motivation

A merchant wants to accept Lightning payments through a PoS device. The PoS
needs to present orders, display payment confirmations, and record payments
for accounting. Existing solutions (LNURL/LUD-21) require centralized callback
servers. This proposal provides a decentralized alternative using BOLT 12 offers
and onion messages.

## Specification

### Actors

- **Customer**: standard BOLT 12 wallet, no modifications required.
- **PoS**: Lightning node without payment channels, communicates via onion
  messages only.
- **Merchant**: always-online Lightning node with channel liquidity.

### Offer Template

The merchant creates an offer template and provides it to the PoS. The template
is a standard BOLT 12 offer with:

- No amount and no description (filled per-order by the PoS)
- `offer_issuer_id`: static public key for PoS delegation
- `offer_paths`: blinded paths to the merchant for invoice requests
- `offer_features`: feature bit TBD set, signaling support for this protocol

The key derivation for template offers MUST exclude TLVs added by the PoS
(amount, description, `encrypted_payment_token`, `notification_path`) so that
the merchant can reconstruct the signing key from the template's original TLVs
and the nonce.

### Offer TLVs

The `encrypted_payment_token` field contains the expected payment amount and
order identifier, encrypted to the merchant's public key with a MAC:

1. type: TBD (`encrypted_payment_token`)
2. data:
   - [`...*byte`:`encrypted_blob`]

The encrypted blob, once decrypted by the merchant, contains:

- [`u64`:`amount`]
- [`...*byte`:`order_id`]
- [`32*byte`:`mac`]

The `notification_path` field contains one or more blinded onion message paths
back to the PoS:

1. type: TBD (`notification_path`)
2. data:
   - [`...*byte`:`blinded_path`]

The blinded path's message context carries the amount and order identifier,
encrypted to the PoS.

### Onion Message TLVs

The `payment_notification` message is sent by the merchant to the PoS when

2. data:

   - [`32*byte`:`preimage`]

### Feature Bit

A new feature bit is defined for `offer_features`:

| Bit  | Name                         | Description |
|------|------------------------------|-------------|
| TBD  | `pos_payment_notifications`  | Merchant supports the bLIP-0056 payment notification protocol |

The PoS MUST check that this feature bit is set in the offer template before
constructing per-order offers. If the bit is not set, the PoS MUST NOT add
`encrypted_payment_token` or `notification_path` TLVs to the offer.

### Per-Order Offer Construction

For each order, the PoS constructs a complete offer from the template by adding:

- `offer_amount`: the order total
- `offer_description`: human-readable order description
- `encrypted_payment_token`: amount and order ID encrypted to the merchant's
  `offer_issuer_id`, with a MAC for authenticity verification
- `notification_path`: blinded path to the PoS, with amount and order ID in
  the message context

The PoS presents this offer to the customer as a QR code.

### Requirements

#### Invoice request flow

The writer of `invoice_request`:

- MUST send the `invoice_request` to the merchant via the offer's blinded
  paths, as per standard BOLT 12.

The reader of `invoice_request` (merchant):

- If the offer's `offer_issuer_id` matches the PoS delegation key:
  - MUST reconstruct the signing key using the nonce, excluding PoS-added
    TLVs.
  - MUST decrypt the `encrypted_payment_token` using its private key.
  - MUST verify the MAC.
  - MUST reject the `invoice_request` if the amount in the token does not
    match the `invoice_request` amount.
  - MUST embed the `notification_path` in the `path_id` field of its blinded
    payment paths (BOLT 4 `encrypted_data_tlv`).
  - MUST send back an `invoice` as per standard BOLT 12.

#### Payment notification

When the merchant receives and claims the payment:

- MUST extract the `notification_path` from the `path_id`.
- MUST send a `payment_notification` to the PoS via the notification blinded
  path.
- MUST include a reply path for acknowledgement.
- SHOULD retry until a `notification_ack` is received (onion messages are
  best-effort).

The reader of `payment_notification` (PoS):

- MUST decrypt the order context from the notification path's message context.
- MUST verify that `amount_msat` is sufficient for the expected order amount.
- MUST verify that hashing the `preimage` produces the `payment_hash`.
- MUST send `notification_ack` if verification succeeds.

### Rationale

The protocol uses two encrypted artifacts that carry overlapping data (amount,
order ID) for different parties at different stages:

- `encrypted_payment_token` is readable by the merchant at invoice request
  time. The merchant decrypts it, verifies the MAC, and compares the amount
  against the `invoice_request`. This provides **pre-payment validation**:
  tampered amounts are rejected before any payment occurs.

- `notification_path` message context is readable by the PoS at notification
  time. The PoS decrypts it to recover the order ID and expected amount,
  enabling **post-payment reconciliation**.

The `notification_path` MUST be constructed by the PoS per-order, not included
in the template. The receiver of a blinded path should always be the one to
construct it.

The merchant treats the `notification_path` as opaque throughout the protocol.
It is embedded in the `path_id` at invoice time and extracted at payment time,
allowing the merchant to operate statelessly without storing per-order data.

The MAC in the `encrypted_payment_token` prevents a malicious party from
crafting a valid token without knowing the merchant's key.

## Backwards Compatibility

The base flow requires no sender-side changes. Any BOLT 12 wallet works.

The merchant must support template offer identification, payment token
decryption, notification path embedding, and sending payment notifications.

The PoS requires constructing offers from templates, creating both encrypted
artifacts, and handling payment notifications.
